# Prompts for loop version 2

Templates for the agents in [`../loop-design-v2.md`](../loop-design-v2.md). Fill the `{…}` fields at run time.
Every agent gets the shared rules first.

## Shared rules (prepend to every prompt)

```
Do not open any file in this repository except the input paths named below, and write only to the output
paths named below. Never use memory as a source. Quote only words you have seen, 40 words or fewer. Grade
every record: P (primary source opened and read, or a transcript you read), R (reputable secondary source
opened), S (search summary only). Don't use these words unless a source uses them in a quote: protocol,
protocol vision, protocol engineering, BPM, hardness, time to amend.
```

## Collector, S1: postings for existing occupations

```
Your task is to measure what postings for existing jobs ask people to do now. For each occupation in
{OCCUPATIONS}, find 8 recent postings (2025–2026) on employer career pages or job boards that show the
full text. Find them by occupation title and location only. Do not add AI, agent, automation or similar
words to your searches. For each posting, record every listed duty as an activity record, with the same
`doc` ID. Add `has_agent_duty` (yes/no) and `has_rule_duty` (yes/no: setting or changing approvals,
limits, permissions, policies or escalation conditions) to each posting's first record.
Write JSON Lines to {OUTPUT}. Fields: id, doc, occupation, activity, object, performed_by, performer_type
(person|agent|both), change, decision, knowledge, functions, quote, source, date, grade, has_agent_duty,
has_rule_duty. At most 5 records per posting: choose the five that are most specific, not the ones that
mention AI. Reply with counts by occupation and the share of postings with agent and rule duties.
```

## Collector, S6: rule-change events

```
Your task is to collect documented events in which a company changed, kept or retired a rule that people or
automated agents act under: incident postmortems, policy changelogs, published internal policies,
approval or expense policies rewritten for automation, audit findings, enforcement actions. Include events
from any industry from 2023 to 2026. For each event, record the activities people performed (who noticed,
who decided, who changed what, who checked), one record per activity, same `doc` per event, at most 5 per
event. Add `functions_named` (all teams the event names) and `named_owner` (the role named as able to
change the rule, or empty). Write JSON Lines to {OUTPUT} with the v1 fields plus performer_type,
functions_named, named_owner. Target 40–60 records. Reply with counts and the events that named an owner.
```

## Extractor, S7: practitioner speech

```
Read the transcript at {TRANSCRIPT}. Its metadata: {ROW}. Extract one record per activity that a speaker
says they or their team do at work, with the timestamp where it is said. Skip opinions, predictions and
product pitches. Fields: id ({MID}-01…), doc ({MID}), activity, object, performed_by, performer_type,
speaker_relation (self|own team|other team|general claim), change, decision, knowledge, functions, quote,
timestamp, source, date, grade (P). Write JSON Lines to {OUTPUT}. At most 12 records per transcript; if
there are more, keep the most specific. Reply with the count and three activities you were unsure how to
record.
```

## Seed writer

```
Write 20 activity records in the JSON Lines format of {EXAMPLE_PATH}, modelled on practice documented in
fields other than AI agents (site reliability, aviation safety, retail credit, insurance claims, quality
management). Ten must show: reviewing overrides, exceptions, escalations, workarounds or failures and
naming the rule or gap they reveal. Five must show: a decision to change, keep or retire a rule, limit or
threshold, naming two or more functions or a trade-off. Five must show: setting or changing what people or
systems may do. Write them in the plain style of the example records; don't make them more explicit than
real records. Write the records to {OUTPUT} and their intended codes to {KEY} (id, code). Don't use the
words listed in the shared rules.
```

## Coder, version 2

```
Read only {POOL}. Assign each record up to two codes using these observable proxies.
PV: reviewing overrides, exceptions, escalations, workarounds or agent failures and naming a rule, a gap
between the written and the actual rule, or a change that followed; or mapping who may approve, see or
change what across teams.
PE: setting, changing or testing what people or agents may do: permissions, limits, approval gates,
escalation and hand-off conditions, never-answer lists, policies an agent reads, interfaces between teams
or agents.
RD: a decision to change, keep or retire a rule, limit or threshold, where two or more functions are named
or a trade-off is stated.
AO: building, prompting, tuning, supplying content to, monitoring or fixing an agent, where no rule others
rely on is set.
OT: anything else.
Boundary: setting an agent's escalation, hand-off or never-answer conditions is PE; writing its prompts,
content or tests is AO; applying an existing rule is OT.
Write JSON Lines to {OUTPUT}: {"id", "codes": ["..", ".."], "note": under 20 words}. Every record once.
Reply with counts per code.
```

## Clusterer, version 2

```
Read only {POOL}. Group records that describe work people do (performer_type person or both) into 6–15
clusters, by evidence of bundling in this order: the same person or team describing several activities;
the same performer across documents; the same decision; the same knowledge. Records listed together in a
regulation, standard or vendor guide (field `duty_set` = true) are a duty set: they may join a cluster
only through a performer, decision or knowledge shared with records outside the duty set. Name clusters by
the work, not by titles. For each: roles that would hold it, whether a stable title exists, seniority at
first hire, whether the holder owns a number (name it, citing records), lasting or transitional, and
confidence. Write JSON to {OUTPUT} in the v1 format plus `owned_number` per role. Validate that every
eligible record appears exactly once.
```

## Calibration coder

```
Read the transcript or notes at {TRANSCRIPT} for item {ROW} (a historical recording about the role
{ROLE}). Record, with timestamps: (a) activities the speaker says they or their team did; (b) any
description of where their authority came from: an agreement on a trade-off, a mandate, a budget, a
number they owned, a policy signed by someone senior; (c) whether the speaker uses the role's title. Code
only what the recording says. Don't comment on whether the role lasted. Write JSON to {OUTPUT}:
{"id", "date", "activities": [...], "authority": [{"text", "timestamp", "quote"}], "title_used": yes|no}.
```
